# Вывод

## Что проверяли

Один и тот же вопрос о Замоскворецкой линии был задан с разным уровнем контроля формата: без ограничений, с JSON-инструкцией, с лимитом `max_tokens`, со `stop`-последовательностью, с JSON mode и с JSON Schema.

## Результаты

- `baseline`: JSON разобран в 0/3, обрезано в 1/3 прогонов.
- `format`: JSON разобран в 3/3, схема соблюдена в 3/3.
- `max_tokens`: ответ обрезан в 3/3, JSON разобран в 0/3.
- `stop`: JSON разобран в 0/3.
- `json_mode`: JSON разобран в 3/3, схема соблюдена в 0/3.
- `schema`: JSON разобран в 3/3, схема соблюдена в 3/3, поля верны в 0/3.

## Вывод

В этих прогонах JSON-инструкция дала разбираемый JSON во всех 3 случаях, но это мягкий контроль: инструкция не гарантирует структуру и требует проверки схемой.
Baseline иногда упирается в технический лимит генерации: 1/3 прогонов обрезаны. Это не форматный контроль, а ограничение длины ответа.
Жёсткий лимит `max_tokens` обрезает ответ и разрушает JSON: 3 из 3 прогонов обрезаны.
`stop`-последовательность обрывает структуру раньше её завершения: разбираемость падает до 0/3.
JSON mode гарантирует синтаксис, но не структуру: JSON валиден в 3/3, а схема соблюдена только в 0/3.
JSON Schema повышает соблюдение структуры по сравнению с JSON mode.
Схема гарантирует форму, но не правильность значений: поля верны в 0/3 при валидной схеме в 3/3.
Содержание не совпало с эталоном ни в одном варианте: локальная модель ошиблась в фактах. Это ограничение знаний модели, а не формата; для проверки содержания нужен внешний источник или web-поиск, которого в ТЗ Дня 2 нет.

Для строгого формата нужен машинно-проверяемый контракт: JSON Schema плюс клиентская валидация и проверка значений. Инструкция в промпте остаётся мягким контролем, а `max_tokens` и `stop` несовместимы с гарантированно целым JSON.
