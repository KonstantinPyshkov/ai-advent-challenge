# Архитектура проекта

## Общая схема

Проект организован как набор независимых экспериментов: каждому дню курса
соответствует отдельный каталог. Общий код выносится в `core` только при
наличии реального повторного использования. День не зависит от внутреннего
устройства других дней; `core` не содержит знаний о конкретных заданиях.

```text
days/day_01/  — минимальный пример без core
days/day_02/  — эксперимент на основе core
days/day_03/  — эксперимент на основе core
days/day_04/  — эксперимент на основе core
days/day_05/  — эксперимент на основе core
core/         — исполнитель: клиент LLM, запуск прогонов, проверки, отчёты
cli/          — единая точка входа: lab day2 / day3 / ...
```

`core` и `cli` будут добавлены начиная со Дня 2. День 1 реализован отдельным
модулем, поскольку по условию требуется минимальный пример без общего
движка.

## Каталог дня

Все материалы дня хранятся в его каталоге:

```text
days/day_02/
├── README.md
├── docs/          # ТЗ, гипотеза, дизайн, runbook, результаты, вывод
├── config/        # настройки только этого дня
├── data/          # датасет, схемы, эталоны
├── prompts/       # промпты, включая промпт для автоматического формирования выводов
├── src/           # код эксперимента
├── logs/          # runs.json, analysis.json
├── reports/       # report.md, report.csv
└── conclusions/   # facts.md, ai.md, conclusion.md
```

День 1 использует сокращённый набор: `config/`, `docs/`, `prompts/`,
`logs/`, `src/`. День 1 не формирует отчёт и выводы, поскольку является
проверкой интеграции с моделью, а не полноценным экспериментом.

## Разделение ответственности

- **День** описывает задачи, варианты, шаги, проверки и требования к отчёту.
- **Core** выполняет очистку выходных каталогов, проверку их пустоты,
  прогрев модели, отправку запросов, журналирование, расчёт метрик и
  формирование отчёта.
- **CLI** определяет, какой эксперимент запускается для выбранного дня.

День не выполняет HTTP-вызовы напрямую. Core не зависит от конкретных дней.

## Метрики

Таймер включается непосредственно перед HTTP-запросом и выключается сразу
после получения тела ответа. Очистка, чтение данных, проверки, формирование
отчёта и запись журнала в `requestMs` не входят и при необходимости
фиксируются отдельными полями.

## Повторный запуск

При каждом запуске дня core удаляет только сгенерированные артефакты
(`logs/`, `reports/`, `conclusions/`), проверяет их пустоту и только после
этого выполняет запрос. Код, `docs/`, `data/`, `prompts/` и `config/` не
изменяются.

## Модели и провайдеры

В текущей версии используется только локальный Ollama. На уровне
архитектуры предусмотрен интерфейс `ChatModel`:

- `OllamaClient` — локальный вызов;
- `OpenAiCompatibleClient` — вызов внешнего API по ключу.

Ключи хранятся только в переменных окружения или
`config/local.properties` (файл исключён из git) и не попадают в журналы,
отчёты и репозиторий.

## Фиксация результата

День считается финальным после локального коммита и установки тега
`day-NN`. Промежуточные прогоны не коммитятся; повторный запуск дня
очищает его выходные каталоги.
