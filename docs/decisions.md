# Зафиксированные решения

## Стек и интерфейс

- Язык и система сборки: Java 21 + Maven.
- Интерфейс взаимодействия: CLI.
- Формат результатов: Markdown и CSV; реализован в Днях 2–3.
- Единая точка входа: `./scripts/run.sh`; без аргументов открывается
  интерактивный выбор дня и модели. Провайдер и API-модель можно
  переопределить флагами `--provider` и `--model`.

## Архитектура

- Общий код вынесен в `core`: клиент Ollama, runner, workspace, проверки,
  отчёт.
- `cli` содержит точку входа и запускает эксперименты через `core`.
- Каждый день оформлен отдельным Maven-модулем в `days/`.
- День 1 остаётся отдельным модулем без `core`.

## Модели

- Основной локальный провайдер: Ollama, нативный эндпоинт `/api/chat`.
- День 3 использует DeepSeek `DeepSeek-V4.1-Flash` (API id:
  `deepseek-flash`) через OpenAI-совместимый `/chat/completions`; ключ
  берётся из `DEEPSEEK_API_KEY`.
- Облачные провайдеры не логируют ключи и не сохраняют их в репозитории.
- Для Дня 1 используется минимальная модель `qwen3.5:2b-mlx`.
- Для Дня 2 используется `qwen3.5:35b-a3b`: вопрос фактический, нужен запас
  знаний и устойчивость к вложенной схеме.
- Распределение моделей по дням: 1 — 2B, 2 — 35B, 3 — DeepSeek, 4 — 9B,
  5 — 2B + 9B + 35B.
- День 3 использует DeepSeek: `off` — `thinking.type=disabled`,
  `on` — `thinking.type=enabled` и `reasoning_effort=high`.
- В Дне 3 нет повторов: ТЗ их не требует; разброс температуры — тема Дня 4.
- `panel` в Дне 3 — один вызов с ролями, а не три независимых агента.
- В `prompt_then_solve` оба шага выполняются в одном режиме рассуждения.
- Ключ и клиент проверяются до очистки каталогов, чтобы ошибка
  конфигурации не удаляла результаты предыдущего прогона.
- Ключ DeepSeek ищется в `DEEPSEEK_API_KEY`, затем в macOS Keychain
  (`deepseek-api-key`); это позволяет не экспортировать переменную в
  каждом новом терминале.
- Перед очисткой каталогов выполняется прогрев/проверка модели: ошибка
  недоступной модели не должна удалять артефакты предыдущего прогона.
- `--report-only` берёт модель и число повторов из `runs.json`, а не из
  флагов командной строки.
- HTTP 4xx (кроме 429) не ретраится; ретраи остаются для транспорта,
  таймаутов и 5xx.
- Матрица по задачам агрегирует все повторы: `✅`, `◐`, `❌`, `⚠️`, `💥`.
- Ключевая логика покрыта самопроверками `./scripts/test.sh` без внешних
  тестовых зависимостей; `./scripts/check.sh` — сборка, тесты и dry-run
  перед новым днём.

## Выполнение экспериментов

- Повторный запуск дня очищает только `logs/`, `reports/` и `conclusions/`.
- Метрики времени рассчитываются только вокруг HTTP-запроса.
- Журналы и отчёты хранятся в каталоге дня.
- Ключи API размещаются только в переменных окружения или
  `config/local.properties` и не попадают в git.
- Выводы Дней 2–3 формируются по правилам, без отдельного AI-нарратива.
- Ollama 0.40.15 не применяет `stop` в `/api/chat`; параметр отправляется,
  а обрезка для варианта `stop` выполняется клиентом. Ограничение отмечено
  в отчёте.
- Пустой `content` не ретраится: повтор с теми же параметрами не меняет
  результат. Ретраи остаются только для сетевых ошибок, таймаутов и HTTP.
- Ответ модели сохраняется в журнале даже при пустом `content`; причина
  классифицируется как `output_limit`, `context_overflow`, `empty_content`,
  `truncated`, `timeout` или `http_error`.
- Технические сбои показываются в отчёте отдельно и не считаются ошибкой
  способа, но входят в знаменатель таблицы.
- Финальная версия дня фиксируется локальным коммитом и тегом `day-NN`.
- Отправка изменений в удалённый репозиторий (push) не выполняется.
